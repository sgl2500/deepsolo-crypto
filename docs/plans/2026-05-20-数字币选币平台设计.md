# 数字币选币平台设计方案

> 第一版基于 `项目介绍.md`、`功能参考图/选币查询.png` 和本地数据源结构整理。当前设计默认这是一个桌面端优先、单人/小团队使用的本地分析平台；后续可以演进为多人 Web 服务。

## 1. 产品定位

这个平台的核心目标不是“展示行情”，而是“基于分钟级原始数据，用可复用指标和公式快速筛选合约，并沉淀买点逻辑”。

平台应该围绕四件事设计：

1. **看数据是否可用**：知道今天/某天有哪些合约、哪些周期、数据是否完整。
2. **生产指标**：把 OHLCV 原始字段加工成可解释、可复用、可预计算的指标。
3. **组织指标**：把验证过的指标放入指标仓库，支持版本、标签、依赖、复用。
4. **选币与标记买点**：在指定时间点组合多个条件，得到合约列表，并保存当时的筛选逻辑、结果快照和买点标记。

## 4. 核心页面设计

### 4.1 选币查询

这是平台主页面，布局参考 `功能参考图/选币查询.png`：

```text
┌─────────────────────────────────────────────────────────────┐
│ 顶部栏：平台名 / 数据新鲜度 / 当前数据源 / 快捷入口          │
├──────────┬──────────────────────────────────────────────────┤
│ 左侧导航 │ 操作工具栏：取值字段 / 批量取值 / 筛选条件 / 临时公式 │
│          ├──────────────────────────────────────────────────┤
│          │ 条件卡片区：每个条件显示命中数量、开关、编辑入口       │
│          ├──────────────────────────────────────────────────┤
│          │ 时间控制：日期 / 周期 / as-of 时间 / 前后切换 / 刷新    │
│          ├──────────────────────────────────────────────────┤
│          │ 结果表格：合约维度表 + 指标列 + 命中原因 + 买点标记     │
│          └──────────────────────────────────────────────────┤
│          │ 右侧抽屉：K线、指标曲线、条件解释、结果快照            │
└──────────┴──────────────────────────────────────────────────┘
```

关键能力：

- **时间查询**：用 `as_of` 表达“站在某个时间点选币”，而不是简单查某一天。
- **周期切换**：支持 `1m / 5m / 15m / 1H`，条件必须绑定周期，避免混用口径。
- **条件卡片**：每个条件显示命中数量，例如“15m 近 4 根涨幅 > 3%，命中 18 个”。
- **命中解释**：结果表里增加 `命中原因`、`失败条件`、`买点标签`，方便复盘。
- **结果快照**：保存策略、公式版本、数据时间、命中合约和指标值，保证未来可复现。
- **详情抽屉**：点击合约后展示 K 线、指标历史、条件逐条通过情况、买点所在 K 线。

推荐表格列：

```text
序号 | 合约 | 最新价 | 24h涨幅 | 当前周期涨幅 | 成交额 | 量能倍数 |
趋势状态 | 波动率 | 命中条件 | 买点标签 | 更新时间
```

### 4.2 指标生产

指标生产用于把原始数据加工成可复用字段。页面分为三栏：

```text
左：字段与函数面板
中：公式编辑器 + 参数配置
右：样例预览 + 校验结果 + 最近计算结果
```

指标定义建议包含：

- 指标名称：例如 `近15分钟涨幅`
- 指标 key：例如 `ret_15m`
- 绑定周期：`1m / 5m / 15m / 1H`
- 输出类型：`number / percent / boolean / category`
- 公式 DSL：例如 `pct_change(close, 15)`
- 依赖指标：例如依赖 `vol_quote_ma_60`
- 计算模式：`实时按需 / 每日预计算 / 增量预计算`
- 状态：`草稿 / 已发布 / 已废弃`

公式必须使用安全 DSL，不直接执行用户输入的 Python/JS。示例：

```text
pct_change(close, 15) > 3
sum(vol_ccy_quote, 5) > sma(vol_ccy_quote, 60) * 2
close > ema(close, 20) and rsi(close, 14) > 60
```

校验规则：

- 字段是否存在。
- 函数参数是否合法。
- 窗口长度是否大于当前数据长度。
- 是否引用了未发布或循环依赖的指标。
- 同一公式在样例合约、样例日期上是否能算出结果。

### 4.3 指标仓库

指标仓库是“已发布指标”的管理中心，目标是让选币查询可以放心复用。

建议列表字段：

```text
指标名称 | key | 周期 | 输出类型 | 单位 | 标签 | 版本 |
发布状态 | 数据新鲜度 | 被引用次数 | 最近计算耗时 | 创建时间
```

关键操作：

- 复制为新指标。
- 查看公式与依赖图。
- 查看历史版本差异。
- 一键加入选币字段。
- 一键创建筛选条件。
- 废弃指标但保留历史快照。

重要规则：

- 已发布指标不允许直接覆盖公式，只能创建新版本。
- 选币快照必须记录当时使用的指标版本。
- 废弃指标不能新增引用，但历史策略仍可复现。

### 4.4 数据源管理

当前只有一个本地数据源，但仍然需要“管理”能力，因为数据每天自动更新，平台要知道数据是否完整。

页面能力：

- 数据源卡片：路径、状态、最后扫描时间、目录大小。
- 周期覆盖：`1m / 5m / 15m / 1H` 各有多少日期、最新日期。
- 日期覆盖：每一天有多少合约文件、是否明显缺失。
- 合约覆盖：某个合约有哪些日期和周期。
- 文件预览：展示前 N 行、字段、时间范围。
- 数据质量：重复 K 线、缺失 K 线、`confirm=0`、异常价格/成交量。

注意：原始 `normalized_gzip` 目录应该只读，平台的索引、缓存、指标结果写入自己的工作目录，避免污染上游数据。

## 6. 推荐技术架构

### 6.1 架构选择

推荐采用 **本地优先的模块化单体**，而不是一开始做微服务。

原因：

- 当前数据源是本机文件目录。
- 数据规模约 GB 级，DuckDB/Polars 能很好处理。
- 需求核心在公式、指标、查询体验，不在分布式服务治理。
- 单人/小团队维护时，微服务会带来不必要的部署和排障成本。

### 6.2 高层架构

```text
┌───────────────────────────────────────────────────────────┐
│ Desktop Web UI                                             │
│ React/Vite + TanStack Table/AG Grid + ECharts/Lightweight  │
└─────────────────────────────┬─────────────────────────────┘
                              │ HTTP/WebSocket
┌─────────────────────────────▼─────────────────────────────┐
│ API Layer                                                   │
│ FastAPI: query / indicators / data-sources / snapshots      │
└───────────────┬───────────────────────────┬───────────────┘
                │                           │

│ Formula Engine                │ │ Job Worker/Scheduler      │
│ Safe DSL -> AST -> SQL/Plan   │ │ scan / compute / refresh  │
└───────────────┬──────────────┘ └──────────┬───────────────┘
                │                           │
┌───────────────▼───────────────────────────▼───────────────┐
│ Analytics Storage                                          │
│ DuckDB + Parquet cache for bars and materialized indicators │

                │                           │

│ SQLite/Postgres               │ │ normalized_gzip csv.gz    │
└──────────────────────────────┘ └──────────────────────────┘
```

### 6.3 技术栈建议

MVP 推荐：

- 前端：React + Vite + TypeScript。
- 表格：TanStack Table + TanStack Virtual；如果需要企业级列管理和大表交互，可用 AG Grid Community。
- 图表：TradingView Lightweight Charts 或 ECharts。
- 后端：Python FastAPI。
- 计算：DuckDB + Polars。
- 元数据：SQLite；如果后续多人协作，再迁移 PostgreSQL。
- 后台任务：APScheduler/RQ；复杂后再上 Celery。
- 运行形态：本地 Web 服务，浏览器访问 `localhost`；MVP 不做 Tauri/Electron 桌面封装。

不建议 MVP 直接上：

- 微服务。
- Kubernetes。
- 实时流计算平台。
- 复杂权限系统。
- 多交易所数据接入。

## 8. 指标与公式系统

### 8.1 公式 DSL 分层

建议把公式分成三层：

1. **字段层**：`open/high/low/close/vol/vol_ccy_quote`
2. **函数层**：`pct_change/sma/ema/sum/max/min/rank/zscore/cross`
3. **条件层**：`ret_15m > 3 and vol_ratio_60 > 2`

### 8.2 公式执行流程

```text
用户输入公式
  ↓
词法/语法解析
  ↓
生成 AST
  ↓
检查字段、函数、依赖、窗口
  ↓
编译为 DuckDB SQL 或 Polars 表达式
  ↓
样例预览
  ↓
保存草稿/发布
  ↓
按需计算或预计算
```

### 8.3 初始内置指标

## 9. 查询执行逻辑

选币查询必须以 `as_of_ts` 为核心。

```text
输入：
  timeframe = 1m
  as_of = 2026-05-20 15:30:00 Asia/Shanghai
  conditions = [
    ret_15m > 3,
    vol_ratio_60 > 2,
    close > ema20
  ]

执行：
  1. 找到 as_of 之前最后一根已确认 K 线。
  2. 加载该时间点所需基础字段和指标。
  3. 对每个条件计算布尔结果。
  4. 按 AND/OR 组合过滤。
  5. 生成结果表、命中原因和快照。
```

要支持两种查询模式：

- **快照查询**：只看某个时间点的结果，速度优先。
- **时光穿梭**：连续切换多个时间点，适合复盘买点出现过程。

## 10. 失败模式与处理

| 场景 | 用户表现 | 处理方式 |
| --- | --- | --- |
| 数据目录不存在 | 数据源红色异常 | 显示路径、最近成功扫描时间、重试按钮 |
| 当天数据不完整 | 最新日期合约数异常少 | 显示“增量中/未完整”，查询默认使用最近完整日期 |
| 公式错误 | 指标无法保存 | 标出错误位置，给出字段/函数建议 |
| 指标依赖缺失 | 查询字段为空 | 显示依赖指标和最近计算状态 |
| 查询耗时过长 | 表格 loading | 支持取消查询，提示建议预计算 |
| 结果为空 | 空状态 | 展示每个条件逐步过滤后的剩余数量 |
| 原始文件更新 | 结果可能变化 | 快照记录文件 mtime/data_version |

## 11. 非功能要求

MVP 目标：

- 选币快照查询：缓存命中时 p95 小于 500ms。
- 未缓存单日查询：常见条件 p95 小于 3s。
- 指标预计算：允许后台分钟级完成，但必须可见进度。
- 表格：支持至少 5,000 合约/行的虚拟滚动。
- 原始数据：只读访问，不破坏 `normalized_gzip`。
- 可追溯：任何选币结果能回看到策略版本、指标版本、数据时间。
- 可维护：公式、指标、查询日志都可导出为 JSON。

## 12. 关键架构决策 ADR

### ADR-001：采用模块化单体，而非微服务

- 决策：MVP 使用一个后端应用承载 API、公式、任务调度，模块内部分层。
- 理由：本地数据源、单机分析、需求还在快速变化。
- 代价：未来多人协作和横向扩展时，需要拆分服务或迁移部署。

### ADR-002：DuckDB + Parquet 作为分析层

- 决策：原始 `csv.gz` 建索引，常用数据和指标结果落 Parquet，用 DuckDB 查询。
- 理由：适合本地 OLAP、时间序列切片、宽表筛选，部署简单。
- 代价：并发写入和多人权限不是强项，后续可迁移 Postgres/ClickHouse。

### ADR-003：公式使用安全 DSL

- 决策：用户公式解析为 AST，再编译为 SQL/表达式，不执行任意代码。
- 理由：避免安全风险，也便于做依赖分析、版本管理和错误提示。
- 代价：前期需要实现函数白名单和解析器。

### ADR-004：结果快照必须版本化

- 决策：保存每次选币的条件、指标版本、数据版本和结果。
- 理由：选币和买点必须能复盘，否则平台无法验证策略有效性。
- 代价：需要额外存储，但数据量可控。

## 13. MVP 交付路径

### 阶段 1：数据可见 + 基础选币

- 数据源扫描与分区索引。
- 选币查询页面骨架。
- 时间点选择、周期选择。
- 内置 8-10 个基础指标。
- 条件卡片 + 结果表格 + 空状态。

### 阶段 2：指标生产 + 指标仓库

- 公式编辑器。
- 公式校验与样例预览。
- 指标保存、发布、版本管理。
- 指标预计算任务。
